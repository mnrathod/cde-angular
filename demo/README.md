# Embed demo

A host application that frames the viewer, so the integration contract in
[`docs/viewer-embed-protocol.md`](../docs/viewer-embed-protocol.md) can be read
as working code rather than as prose.

**It is not the viewer.** Everything in `demo/` is the *other* side — the thing
an integrator writes. It is plain HTML, CSS and JavaScript with no framework,
no build step and no dependencies, because that is the claim the iframe embed
makes: your stack is your business. A demo host written in Angular would prove
nothing.

---

## Run it

```bash
# 1. the viewer, on :4200
npm start

# 2. the host, on :4401, in another terminal
node demo/server.mjs
```

Then open <http://localhost:4401>.

Two ports, deliberately: a different port is a different origin, so the demo
exercises the real cross-origin path — origin checks on every message, CORS on
the document fetch, `frame-ancestors` on the viewer. A demo served from one
origin would pass with every one of those broken.

If the viewer is somewhere else:

```bash
VIEWER_ORIGIN=https://viewer.example node demo/server.mjs
```

The page reads that value from `/config.json` rather than having its own copy,
because the server uses the same value for `Access-Control-Allow-Origin`. When
those two disagree the frame loads and the document silently does not, which
looks like a protocol fault and is not one.

### What you need on the viewer side

The viewer must allow this origin to frame it. `frame-ancestors 'none'` is the
default on every route (CLAUDE.md §5.4) and the embed route is the documented
exception (ADR 14) — in a real deployment it is sourced from tenant
configuration, never a wildcard.

## What to try

| Do this | See this |
|---|---|
| Choose a document | The handshake in the message log: `viewer.ready` → `host.init` → `viewer.loaded` |
| Draw on the drawing | A row appears in "Markup the host has stored", authored by the name in the Session panel |
| Reload the page and reopen the document | The markup comes back. The viewer forgot; the host remembered |
| Change the display name, then draw again | The new name is stamped. The viewer never sent one |
| Tick `document:sign`, then use Sign in the viewer | The control renders and the operation is **refused**. Both are correct |
| Press "Send an empty identity" | The capability-gated controls disappear and the viewer keeps working |
| Open `sample-specification.docx` | A `viewer.error` naming the conversion service — see below |

The last one is the honest part. **Only PDF renders in the browser.** Office
and IFC are converted server-side before the viewer sees pages or geometry
(§6.7.4, §5.13.10), so an embed with no conversion service reachable cannot
open them. It says so, with an RFC 9457 problem detail, instead of showing an
empty frame. Point the viewer at a deployment that has the conversion service
and the same two files open normally.

## The sample files

Three files in `public/files`, all generated by
[`tools/generate-samples.mjs`](tools/generate-samples.mjs) and committed
alongside it.

| File | What it is |
|---|---|
| `sample-drawing.pdf` | Three A3 sheets — a plan with a column grid, a section, and a notes sheet. Vector geometry and a real text layer, so measurement and search have something to work on. Search for `FERROUS`: two hits, both on sheet 3 |
| `sample-specification.docx` | A short Office document. Hand-written OOXML, verified by opening it in LibreOffice |
| `sample-model.ifc` | A small IFC4 model: a site, a building, three storeys, three elements each |

They are generated rather than found, and that is a licence position rather
than a convenience (§17.1). A drawing pulled off the internet carries a licence
someone has to trace before a release; one produced by a script in this
repository carries none. Every byte is ours, no font file is embedded — the PDF
uses only the base-14 fonts — and nothing describes a real project, party,
asset or location (§14).

```bash
node demo/tools/generate-samples.mjs           # rewrite them
node demo/tools/generate-samples.mjs --check   # fail if they are stale
```

The generators are deterministic, which is what makes `--check` usable: fixed
timestamps everywhere, so regenerating produces byte-identical output and a
difference means a real difference.

## Reading the code

Two files, in this order:

1. **[`public/host-protocol.js`](public/host-protocol.js)** — the protocol.
   `ViewerHost` is the channel, `MarkupStore` is persistence, `decideOperation`
   is authorisation. No DOM anywhere in it.
2. **[`public/host.js`](public/host.js)** — one way to build a UI over that.
   None of it is required.

The split is not tidiness. Because the protocol half has no DOM, the repository's
test suite runs it directly against the viewer's own channel — two independent
implementations, neither importing the other, checked against each other rather
than against a shared assumption:

```
src/app/features/embed/protocol-conversation.spec.ts
```

That is also why this is a separate implementation rather than a shared client
library. An integrator writes this file; if the protocol is awkward to
implement, it is awkward here first.

### The minimum

§9 of the protocol is four steps, and everything else in this demo is
additive:

1. Serve a page that frames the viewer with `parentOrigin` set.
2. Listen for `viewer.ready`.
3. Reply with `host.init` carrying a `document.url` you minted.
4. Ignore every other message.

A host that implements only those is a viewing integration, not a broken one.

## Tests

```bash
npx playwright test --config demo/e2e/playwright.config.mjs
```

Runs the host page in a browser against a stub viewer on a third port. It has
its own Playwright config rather than using the repository's, because that one
starts `ng serve` and this needs no build — these tests run in a checkout that
has never built the Angular application, which is the situation someone
evaluating the integration is in.

`e2e/stub-viewer.html` is a fixture, not a second implementation to check the
protocol against. Its job is to give the host page something to frame across a
real origin boundary; the protocol agreement is checked in
`protocol-conversation.spec.ts` against the real viewer.

Two defects found this way and fixed, both invisible to a unit test:

- the host captured `iframe.contentWindow` before assigning `src`, so after
  the frame navigated every inbound message failed the sender check and the
  demo sat silent;
- an author `display` beat the user agent's `[hidden] { display: none }`, so
  the placeholder stayed laid over the frame and swallowed every click into
  the viewer while looking correct in a screenshot.

## What this demo does not show

**Collaboration.** Live cursors and presence need the STOMP socket, which has
no authentication story in an embedded deployment — the one loose end "no
identity" leaves (ADR 14, consequences; protocol, open questions). It is
outside the protocol until that is solved.

**A real minted URL.** The host serves the sample files from its own origin on
a plain path. A real host mints a short-lived signed URL; adding one here would
mean protecting a credential the demo does not otherwise need, and it would not
change a single message.

**A production `frame-ancestors`.** In a real deployment the allow-list comes
from tenant configuration. The stub sets one header to show the shape.
