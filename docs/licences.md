# Licences

The approved licence list, the obligations this repository carries, and every
open finding. CLAUDE.md §2.1 sets the policy; this file records how it is met
here and where it is not.

The backend keeps its own equivalent at `cde-platform/docs/licences.md`. The
two repositories are one product and one licence position — a component
allowed in one and forbidden in the other would be a contradiction, not a
per-repository choice.

---

## 1. How attribution is produced

`THIRD-PARTY-NOTICES.txt` is generated by `scripts/generate-attribution.mjs`
from the resolved production dependency tree in `package-lock.json`, and is
committed. It is not maintained by hand.

```bash
npm run attribution        # regenerate
npm run check:attribution  # fails if stale, uncommitted, or untracked
```

The generator reads the lockfile rather than walking `node_modules`, so it
needs no licence-scanning dependency (§0.3) and works on a checkout that has
not run `npm install`. It **refuses to write the file** when a dependency
carries a forbidden or unrecognised licence: a notices file asserts that the
licences in it are ones we may ship under, and generating one over a
violation would make that assertion false.

`npm run check:attribution` regenerates and then asks git whether anything
changed, rather than checking that the file exists. The backend learned why
the hard way — Bouncy Castle moved 1.78.1 → 1.85 with the shipped attribution
still naming 1.78.1 and every gate green.

**Current state:** 38 production components across four licences — MIT (32),
Apache-2.0 (4), BSD-2-Clause (1), 0BSD (1). All four are on the §2.1 allowed
list. No forbidden or weak-copyleft licence is present, so this repository
carries no copyleft obligation and needs no per-component exception.

## 2. What the attribution covers, and what it deliberately over-covers

The whole production dependency closure, not the subset that survives
tree-shaking into `dist/`. Deriving the latter means parsing build output and
would under-report the moment the bundler changed. Over-attributing costs a
longer list; under-attributing is a breach, so the file errs long.

Two entries are deliberate and should not be "cleaned up":

| Entry | Why it is listed |
|---|---|
| `@napi-rs/canvas` and its 12 per-platform native builds | Optional production dependencies of pdfjs-dist. Any one installation resolves one of them; which one depends on the machine, so all are listed |
| `@types/three` | Declared as a production dependency although it contributes no runtime code. It is attributed as declared rather than as judged |

Development-only dependencies are excluded — the Angular CLI, TypeScript,
Vitest, Playwright and their trees. They are not redistributed and carry no
attribution obligation. npm's own `dev` flag decides, so a package reachable
from `dependencies` is included even when a devDependency also reaches it.

## 3. Open findings

### 3.1 The PWA application icons are the Angular logo — **BLOCKS RELEASE**

**Found 2026-09-09. Not fixed here: replacing them needs the product's own
mark, which is a brand decision rather than an engineering one.**

| | |
|---|---|
| What | `public/icons/icon-{72,96,128,144,152,192,384,512}.png` — eight sizes, all the Angular "A" shield in Angular's pink/purple gradient |
| Where it ships | `public/manifest.webmanifest` lists all eight as the application's icons. An installed PWA shows this on the user's home screen and in their app switcher |
| Where it came from | The defaults from `ng generate @angular/pwa`. Left in place rather than chosen |
| Why it is a problem | §17.4: a third party's logo may not be used without checking their trademark guidelines, and never in a way implying endorsement or affiliation. This is not nominative fair use — the mark is not being used to *refer to* Angular, it is being used *as this product's identity* |
| Fix | Replace all eight with the product's own mark, at the same sizes. Until the product has one, any neutral placeholder that is ours is better than a mark that is not |
| Also check | `manifest.webmanifest` still says `"name": "cde-angular"` and `"short_name": "cde-angular"`, which is the scaffold name rather than a product name |

Angular is a trademark of Google LLC. Using the framework carries no right to
its mark; the MIT licence on the code is a copyright grant and is silent on
trademarks, which is the usual arrangement and the reason this needs fixing
rather than documenting.

### 3.2 The copyright holder is a placeholder

`LICENSE` and `NOTICE` both name `<<< COPYRIGHT HOLDER NOT YET SET >>>`. No
legal entity is recorded anywhere in either repository, and inventing one
would put a false owner on the copyright notice. The same placeholder is in
`cde-platform`; both must name the same holder and should be fixed together.

### 3.3 No licence-change baseline

§17.2 requires the scan to compare against the previously recorded licence
per dependency and fail on any change, so a re-licence is caught at the
upgrade PR rather than at an audit. The backend does this with
`gradle/licence-baseline.txt`. This repository has no equivalent: the
generator checks each licence against the policy, but not against what that
package declared last time.

The risk is real rather than theoretical — §2.2 lists seven components that
re-licensed away from open source since 2021.

### 3.4 `@cde/viewer-core` is marked `UNLICENSED`

Deliberate, and now partially resolved. The marker makes an accidental
`npm publish` fail rather than quietly shipping to a public registry with no
licence position. `LICENSE` and `NOTICE` now exist, so the package is
covered — but the decision to publish it, and under what terms, has not been
taken. Removing the marker is that decision, not a cleanup.

### 4.1 The demo's sample documents

`demo/public/files/` holds three documents that ship with the repository and
are served to anyone running the demo. They are **generated**, by
`demo/tools/generate-samples.mjs`, and committed alongside the generator.

Generating them is the licence position, not a convenience. A drawing, a
specification or an IFC model taken from anywhere else arrives with a licence
someone has to trace before a release, and construction sample data is
particularly bad for this — models and drawings circulate widely with no clear
provenance at all. A file produced by a script in this repository has none to
trace.

| File | Provenance | Notes |
|---|---|---|
| `sample-drawing.pdf` | Generated | PDF written directly by `tools/lib/pdf.mjs`. Uses only the **base-14 fonts** (Helvetica, Helvetica-Bold), which are referenced by name and not embedded, so no font licence attaches |
| `sample-specification.docx` | Generated | Office Open XML written by hand and zipped by `tools/lib/zip.mjs`. Verified by opening in LibreOffice |
| `sample-model.ifc` | Generated | ISO 10303-21 text. Writing a file **in** a published exchange format is implementing the format, not reproducing the specification — §17.5 forbids reproducing a standard's text, tables or code lists, and none of that is present. The entity names are the format's vocabulary, as element names are an XML schema's |

Content: every name, party, location, dimension and identifier is invented
(§14). Nothing describes a real project, organisation, person or asset, and the
sheets say so on their face so a sample opened in front of a customer cannot be
mistaken for a deliverable.

The generator is deterministic, and `--check` fails if the committed files
differ from what it produces — so "these are ours because a script made them"
stays a fact that can be re-verified rather than a claim in this table.

No dependency is used to produce them. The PDF, ZIP and IFC writers are ours,
which is also why they are small and refuse anything they cannot encode
correctly rather than degrading quietly.

No asset is fetched at runtime from a CDN, enforced by
`scripts/check-no-remote-code.mjs`. That gate exists for security, but it is
also what keeps this table true: code or assets arriving from a CDN would be
redistributed to the user without appearing in any manifest, so nothing would
attribute them.
